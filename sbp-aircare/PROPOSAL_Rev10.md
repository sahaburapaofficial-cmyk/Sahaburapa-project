## 1. ระบบรับคำขอจริง (แก้ B4)

### 1.1 ทำไมต้องย้ายที่โฮสต์ก่อน

หน้าใน Claude Artifacts ส่งข้อมูลออกไปโดเมนอื่นไม่ได้ (CSP บล็อก) จึงต่อ backend จาก Artifacts ไม่ได้ ไม่ว่าจะเลือกทางไหน ต้องโฮสต์หน้าเว็บเองก่อน

| ที่โฮสต์ | ค่าใช้จ่าย | ข้อดี | ข้อจำกัด |
|---|---|---|---|
| ★**GitHub Pages** (เลือกแล้ว Rev.10) | ฟรี (repo Public) | อยู่ที่เดียวกับซอร์ส · build อัตโนมัติด้วย GitHub Actions · ลิงก์ถาวร | ผู้ดูแล repo ต้องเปิด Pages ครั้งเดียว · แบนด์วิดท์แนะนำ ~100 GB/เดือน |
| **Cloudflare Pages** | ฟรี | แบนด์วิดท์ไม่จำกัด · เซิร์ฟเวอร์ในไทย/เอเชีย · ใช้ไฟล์ `dist/offline/*.html` ได้ทันที · มี Turnstile กันสแปมฟรีในเครือเดียวกัน | ไฟล์ละไม่เกิน 25 MiB (ของเรา ~2.8 MB ผ่าน) · build 500 ครั้ง/เดือน |
| Netlify / Vercel | ฟรีในระดับเริ่มต้น | ตั้งง่าย | แผนฟรีจำกัดแบนด์วิดท์ · Vercel แผนฟรีห้ามใช้เชิงพาณิชย์ |

ชื่อเว็บช่วง beta: `sbp-aircare.pages.dev` (ฟรีทันที) หรือ `beta.sahaburapa.com` (ต้องมีสิทธิ์แก้ DNS ของโดเมนบริษัท)

ลิงก์ Artifacts เดิมเก็บไว้เป็นเดโมได้ แต่ปุ่มส่งในเดโมจะยังเป็นแบบ "คัดลอกสรุปส่งเอง" เหมือนตอนนี้

### 1.2 ทางเลือก A — Google Apps Script → Google Sheet + อีเมลแจ้งทีม (แนะนำสำหรับ beta)

```
ลูกค้ากดส่ง → POST (JSON) → Apps Script Web App (บัญชี Google ของบริษัท)
   → บันทึกแถวใน Google Sheet "SBP Leads" (แท็บ: ใบเสนอราคา / ติดต่อ / ความเห็น Beta)
   → อีเมลแจ้งทีมขาย 1 ฉบับต่อคำขอ (เลขอ้างอิง + รายการ + ยอดประมาณ + เบอร์ลูกค้า)
   → ตอบกลับเลขอ้างอิง → หน้าเว็บแสดง "ส่งถึงทีมแล้ว เลขที่ …"
   ถ้าส่งไม่สำเร็จ → แสดงตามจริงว่า "ส่งไม่สำเร็จ" + กล่องสรุปแบบเดิม (คัดลอก/อีเมล/โทร)
```

| หัวข้อ | รายละเอียด |
|---|---|
| ต้นทุน | **0 บาท** (Google ฟรี + Cloudflare Pages ฟรี + Turnstile ฟรี) |
| เวลาทำ | ~1–2 วันทำงาน รวมทดสอบ |
| ข้อมูลอยู่ที่ไหน | Google Drive ของบริษัทเอง ทีมขายเปิด Sheet ดู/กรอง/ใส่สถานะได้ทันที |
| ขีดจำกัด | บัญชี Gmail ทั่วไปส่งอีเมลจากสคริปต์ได้ **100 ผู้รับ/วัน** (Google Workspace 1,500) — ถ้าแจ้ง 1 คนต่อคำขอ = รับได้ ~100 คำขอ/วัน · ข้อมูลยังบันทึกลง Sheet ได้แม้โควตาอีเมลหมด |
| ความเสี่ยง | (1) URL ของสคริปต์เป็นสาธารณะ → ต้องกันสแปมด้วย Turnstile + ช่องดักบอท (honeypot) + จำกัดขนาดข้อมูล (2) ถ้าคนทำสคริปต์ลาออก/ลบบัญชี ระบบหยุด → ให้สคริปต์อยู่ในบัญชีบริษัท ไม่ใช่บัญชีส่วนตัว (3) ยอดเงินมาจากเบราว์เซอร์ลูกค้า → บันทึกเป็น "ยอดประมาณการ" ทีมขายยืนยันในใบเสนอราคาจริงเสมอ (คำนวณซ้ำฝั่ง server ทำในเวอร์ชันใช้งานจริง P2) (4) PDPA: ต้องมีข้อความแจ้งวัตถุประสงค์ + ช่องยินยอมในฟอร์ม และกำหนดระยะเก็บข้อมูล |
| ต่อยอด | เพิ่มแจ้งเตือน LINE OA ผ่าน LINE Messaging API ภายหลังได้ (LINE Notify ปิดบริการแล้ว) เมื่อมีบัญชี LINE OA |

### 1.4 คำแนะนำ

ใช้ **ทางเลือก A** ช่วง beta (ไม่มีค่าใช้จ่าย ข้อมูลอยู่ในบัญชีบริษัท ทีมขายใช้ Sheet ที่คุ้นเคย) แล้วย้ายไป API + ฐานข้อมูลของเว็บจริงในเฟส P2 (Next.js) ตามแผนเดิม

**จุดที่จะแก้เมื่ออนุมัติ:** `site.js` §8 (`#qform` ส่งคำขอ) · `commerce.js mountCart` (ส่งใบเสนอราคา) · `site.js openFeedback` (ความเห็น Beta) · `contact.js handoffBox` (ใช้เป็นทางสำรองเมื่อส่งไม่สำเร็จ) · โมดูลใหม่ `assets/submit.js` (ที่อยู่ endpoint เก็บเป็นค่าคงที่ในโมดูล ไม่เพิ่ม global ตามกฎ §6.3) · `build.py` เพิ่มชุด build สำหรับ Cloudflare Pages · เทสต์: smoke + textscan + เทสต์ส่งจริงไปยัง Sheet ทดสอบ

**ต้องการจากเจ้าของก่อนเริ่ม:** เลือกทางเลือก · บัญชี Google ของบริษัทที่จะเป็นเจ้าของสคริปต์/Sheet · อีเมลผู้รับแจ้งเตือน (กี่คน) · บัญชี Cloudflare (หรือให้สร้างใหม่) · จะใช้ `*.pages.dev` หรือโดเมนบริษัท · อนุมัติข้อความแจ้งความเป็นส่วนตัว (ร่างให้ได้)

### 2.3 วัดความลื่นของภาพ 3 มิติ

- ง่ายสุด: ให้คะแนนด้วยตา 1 = กระตุกจนใช้ไม่ได้ · 2 = กระตุกชัด · 3 = พอใช้ · 4 = ลื่น
- ละเอียด: Android ต่อสาย USB → Chrome บนคอมพิวเตอร์ `chrome://inspect` → Rendering → Frame rendering stats · iPhone → Safari บน Mac → Develop → Timelines
- เกณฑ์ตาม HANDOFF §8 ข้อ 4: ต่ำกว่า ~24 fps = ต้องลดภาระ (ข้อ 3)
- (เสนอเพิ่ม เมื่ออนุมัติ) ตัวแสดง fps บนหน้าเว็บเมื่อเปิดด้วย `?fps=1` เพื่อให้คนทดสอบอ่านค่าได้เองโดยไม่ต่อคอมพิวเตอร์

## 3. ถ้าเครื่องไหนช้า: วิธีลดภาระ 3 มิติ (HANDOFF §8 ข้อ 4)

เรียงจากผลมาก/แก้น้อย → ผลมาก/แก้มาก ทำทีละขั้นแล้ววัดซ้ำ

| ลำดับ | วิธี | ผลที่คาด | ผลต่อภาพ | จุดแก้ |
|---|---|---|---|---|
| 1 | **ระดับคุณภาพอัตโนมัติ** ตาม `navigator.deviceMemory`, `hardwareConcurrency`, ขนาดจอ → ต่ำ/กลาง/สูง | ใช้กับทุกฉากในจุดเดียว | ไม่กระทบเครื่องแรง | `gl-pool.js` (เพิ่ม `quality()`) |
| 2 | `pixelRatio` = 1 บนระดับต่ำ (ตอนนี้สูงสุด 2) | ภาระพิกเซลลดได้ ~4 เท่าบนจอความละเอียดสูง | ภาพนุ่มลงเล็กน้อย | ทุก `setPixelRatio` |
| 3 | ปิดเงา (shadow map) บนระดับต่ำ | ลดภาระ GPU มาก | ไม่มีเงาใต้วัตถุ | ฉากที่เปิด `shadowMap` |
| 4 | ลดอนุภาคลม/หยดน้ำลงครึ่งหนึ่ง (`wisp3d`, `airflow3d`) | ลดภาระ CPU/GPU | ลมบางลง ระยะลมที่คำนวณเท่าเดิม (ห้ามแก้ฟิสิกส์ throwsim) | `wisp3d.js`, `airflow3d.js` |
| 5 | จำกัดเฟรม 30 fps + หยุดเรนเดอร์เมื่อภาพไม่เปลี่ยน | ประหยัดแบตและความร้อน | แทบไม่เห็นต่าง | loop ของแต่ละฉาก |
| 6 | งบ WebGL ระดับต่ำ = 1–2 ฉากพร้อมกัน | ลดหน่วยความจำ (สำคัญกับ iPhone) | ฉากไกลจอโหลดใหม่เมื่อกลับมา | `gl-pool.js` |
| 7 | **ลดระดับเองขณะใช้งาน**: ถ้าวัดได้ < 24 fps ต่อเนื่อง 3 วินาที ลดไปขั้นถัดไปอัตโนมัติ | ปรับตามเครื่องจริง | แจ้งเล็ก ๆ "ปรับภาพให้ลื่นขึ้น" | `gl-pool.js` |
| 8 | **แตะเพื่อเริ่ม 3 มิติ** บนระดับต่ำ: แสดงภาพนิ่งของฉากก่อน | เปิดเว็บเร็วขึ้นมาก | ต้องแตะ 1 ครั้ง | ทุก `boot` lazy |
| 9 | วิดีโอสั้นที่อัดจากฉากเราเอง แทนฉากหนักบนเครื่องอ่อน (ขั้นตอนช่าง) | ลื่นทุกเครื่อง | โต้ตอบไม่ได้ในโหมดนั้น | เพิ่มไฟล์วิดีโอ (ทำได้เมื่อโฮสต์เอง ไม่ใช่ Artifacts) |

ต้องการจากผลทดสอบ: ชื่อรุ่นเครื่อง, แบบ A/B/C, ฉากที่ช้า, คะแนน 1–4 (หรือ fps) → จะเลือกชุดวิธีที่เหมาะ แล้ววัดซ้ำก่อน/หลัง

## 4. แนวทางพัฒนาเว็บ (ตามโจทย์: งานล้างเป็นหลัก · B2C + B2B · ภาพ 3D/4D สมจริง · ดึงดูดกว่าคู่แข่ง)

### 4.1 สิ่งที่ต้นแบบมีแข็งแรงแล้ว (ไม่ต้องทำซ้ำ)

ราคาโปร่งใสจาก Pricebook จริง 705 รุ่น · ขั้นตอนช่างตามแบบฟอร์มบริษัท (C1 / C2 / ติดตั้ง / ซ่อม) เป็นภาพ 3 มิติทีมช่าง 2 คน + ลูกค้า · ห้องจำลอง 48 ห้อง · ลองวางแอร์ในห้อง · ตัวคำนวณสัญญาล้างรายปี · แผนที่ค่าเดินทาง — ระดับนี้เหนือเว็บร้านแอร์ทั่วไปในไทยแล้ว ช่องว่างที่เหลือคือ **ความเชื่อมั่น (ของจริง)**, **การปิดการขาย (ส่งคำขอถึงทีมจริง + ติดตาม)** และ **ความสมจริงของภาพ**

### 4.2 ข้อเสนอเรียงตามผลต่อยอดขาย

| 1 | **ส่งคำขอถึงทีมจริง** (ข้อ 1) + ข้อความยืนยันพร้อมเวลาติดต่อกลับ | B2C/B2B | ทุกอย่างที่เหลือไร้ผลถ้าลีดหาย | ตามข้อ 1.4 |

### 4.3 ภาพ 3 มิติให้สมจริงขึ้น — 3 ระดับ

| ระดับ | ทำอะไร | ข้อดี | ข้อเสีย/ต้นทุน |
|---|---|---|---|
| 1. ปรับฉากเดิม | แสงแบบสะท้อนสภาพแวดล้อม (มี `RoomEnvironment` แล้ว) + พื้นผิวสมจริง (โลหะ พลาสติก ผ้า) + เงานุ่ม/เงาสัมผัสพื้น + เอฟเฟกต์หลังเรนเดอร์บนเครื่องแรงเท่านั้น | ใช้โค้ดเดิม ไม่มีค่าใช้จ่าย | ยังเป็นโมเดลจากโค้ด ช่าง/คนยังดูเป็นหุ่น |
| 2. โมเดล GLB ทำโดยนักออกแบบ 3 มิติ | ตัวเครื่องแอร์กลาง ๆ (ไม่ลอกแบบยี่ห้อใด) + ช่างที่มีท่าทางจริง (rig + animation) + เครื่องมือ ปั๊มล้าง ถุงล้าง ใส่ผ่านช่อง `loadModel(url)` ที่มีอยู่ | สมจริงขึ้นชัดเจน ยังโต้ตอบได้ | ต้องจ้างงาน/ซื้อโมเดลที่มีสิทธิ์ใช้เชิงพาณิชย์ · ไฟล์ใหญ่ขึ้น → ต้องโฮสต์เอง |
| 3. วิดีโอเรนเดอร์ภาพยนตร์ (Blender) สำหรับหน้าแรก + ฉากโต้ตอบเป็นส่วนเสริม | สมจริงที่สุด ลื่นทุกมือถือ | สวยระดับโฆษณา | ต้นทุนสูงสุด แก้ไขยาก · ต้องโฮสต์เอง |

แนะนำ: ระดับ 1 ทันทีหลังเลือกแบบ + ระดับ 3 แบบสั้น (15–30 วินาที) เฉพาะหน้าแรกงานล้าง ถ้ามีงบ · ทุกฉากยังต้องมีป้าย "แบบจำลองเพื่ออธิบาย" และห้ามมียี่ห้อบนตัวแอร์ของลูกค้า (§6.6 ข้อ 20)
